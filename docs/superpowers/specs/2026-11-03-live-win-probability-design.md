# Win probability for the selected game on `/live` — design

Date: 2026-11-03. Status: owner approved the approach, layout A (mockup `wp-layout`) and every
"my call" below in chat; written for planning.

## Intent

The owner wants a **result-prediction model** on the public site, applied to **one selected
game** at a time. `/live` already selects a single game (chips, `?game=`). This adds a
"Win probability" section for that game: a pregame prediction before tip-off, then the live
probability and its curve over the whole game, with ESPN's own probability line overlaid as an
honest benchmark.

The idea comes from an AI-Studio demo (`C:\dev\nba-pbp-time-series-engine-(timestral-preprocessor)`,
moved out of the repo): a closed-form "drifting lead" model. The demo itself is not reused
(mock data, hand-picked constants, made-up EPM, Vegas spread, BOS/DAL hard-coded). Only the
model *form* is kept, and its parameters are **fitted on hoops-lab's own data**.

## Goals

1. **Model in Python** (`hoops_lab/`, business logic stays there), fitted on the play-by-play
   sample (about 475 games over 6 seasons) and gated on a temporal holdout.
2. **Export** of the fitted parameters plus every team's current pregame strength to a small
   JSON in `web/public/data/`, regenerated by the existing web export, so the daily refresh
   keeps it current.
3. **Browser side**: for the selected game compute the win probability from ESPN's score and
   clock, show it under the scorebar (layout A) with a curve over the game, and overlay
   ESPN's `winprobability` line.

## Non-goals

- EPM, lineup-impact drift, any player-level term (we have no EPM; BPM may come later).
- Timestral / PyTorch / any foundation model in the product (needs a server or a GPU; not a static site). A later, optional **offline** benchmark of Timestral zero-shot against this model on the same held-out games is possible (separate environment, not in the deploy lock).
- Betting data. ESPN's `pickcenter` spread is **not** used or shown (owner decision).
- Changing the dashboard's existing model (`hoops_lab/models/win_probability.py`); it stays as
  it is and serves as the gate's baseline.
- Games older than yesterday (the `/live` game list is unchanged).

## Anti-goals

- Training on information from the future: the pregame strength of a game must only use games
  played **before** that game's date.
- A confident percentage with nothing behind it: if a team's pregame strength or the model file
  is missing, the section says so instead of showing a number.
- Breaking the hosted dashboard: `dashboard/` must not import anything new from `hoops_lab/` in
  this change (Streamlit Cloud reloads only `dashboard/` modules on push; see CLAUDE.md and the
  theme-import guard test).
- Weakening any design gate; hex colours anywhere in `web/app|components|lib`.

## The model (owner-approved form; fitting choices are my calls)

Expected final margin from the home side = current margin + pregame drift × remaining
fraction; uncertainty shrinks as √(remaining fraction). In logistic form, with no intercept:

```
f      = max(secondsRemaining, 1) / 2880          (remaining fraction of regulation; my call)
z      = a · margin/√f  +  b · √f · (1 − neutral)  +  c · ΔNR · √f
P(home wins) = 1 / (1 + e^(−z))
```

- `margin` = home points − away points. **In training it is summed from scoring events**
  (`features.possession._event_points` after `sort_chronological`), never from the feed's
  `scoreHome`/`scoreAway` snapshots (CLAUDE.md rule).
- `secondsRemaining`: regulation = (4 − period)·720 + clock seconds; overtime = clock seconds
  left in that OT period (same convention as the existing model).
- `neutral` = the game's `neutral_site` flag (home-court term off).
- `ΔNR` = pregame net rating of home − away (below).
- Readable parameters, reported in the export: home court `b/a` points, `c/a` points of
  expected margin per point of net-rating difference, scale `1/a`.
- **Link: logistic, fitted with scikit-learn `LogisticRegression(fit_intercept=False,
  penalty=None)`** (my call): same shape as the demo's normal CDF, no new dependency (scipy
  would be a new direct dependency; `requirements.txt` is the deploy lock).
- **Training samples (my call):** one state per scoring event plus the opening-tip state
  (margin 0, f = 1) per game; label = home won, from `games` final scores.

### Pregame net rating (owner: net rating + home court; leak-free design is my call)

From `box_scores_team` (one row per team per game, all 1 230 games a season):

- possessions per team-game ≈ `FGA + 0.44·FTA − OREB + TOV`; a game's possessions = mean of
  the two teams' estimates.
- **Season-to-date net rating** of a team before date D = 100 × Σ(points − opponent points) /
  Σ possessions over its games of the same season with `GAME_DATE < D`.
- **Blend with last season** (early-season stability, my call): with n prior games this season,
  `prior = (n · NR_to_date + k · NR_last_season_final) / (n + k)`, `k = 10` (a named constant).
  First season in the data (2021-22): `NR_last_season_final` = 0.
- The **same function** produces the training priors (as of each game date) and the exported
  current priors (as of the latest game in the newest season), so training and inference agree.

### Quality gate (my call; integration test, skips without the DB like the others)

> **Amended 2026-11-03 (final review, controller ruling):** the gate — both the integration test and the
> export's self-gate — evaluates on the **two most recent completed regular seasons** (≥ 1230 games),
> training strictly before them; the in-progress season is only logged. A replay showed the in-season
> holdout's ECE above 0.05 for a season's first ~50 games (noise), which would have blocked the daily
> refresh. Thresholds unchanged. Today: train 2021-22..2023-24, held-out 2024-25 + 2025-26.

Train on the PBP sample of 2021-22…2024-25, evaluate on **2025-26 + 2026-27 to date** (about
158 held-out games; one season alone, ~81 games of highly correlated states, is too noisy for
a calibration check):

1. held-out log-loss of the new model **<** held-out log-loss of the existing
   `train_win_probability` model trained on the same seasons;
2. calibration: expected calibration error (10 equal-width bins) **≤ 0.05** on the held-out
   states;
3. pregame only (f = 1, margin = 0) over **all** held-out-season games in `games` (not just
   the PBP sample): log-loss **<** the log-loss of a constant equal to the training home-win
   rate.

The exported model is then fitted on **all** seasons' PBP sample (my call).

**If the gate fails (my call):** the builder may adjust the model **within its family** — the
exponent on `f` in the drift and spread terms, and the blend constant `k` (try e.g. 5/10/20) —
but never add a plain intercept (a time-independent offset would be wrong at the final horn)
and **never relax the thresholds** (gates are not weakened in this project). If no variant
passes, the export does not write the model file and the page shows the "not available" text;
the rest of the feature still ships and the owner is told.

### Which games (my call)

The data and the priors are **regular season only** (`games` and the PBP sample hold only
"Regular Season"). The section is shown for regular-season games (NBA Cup knockout games are
regular season and use the neutral flag), play-in and playoff games (net rating stays
meaningful; documented as an extrapolation in the footnote), and **hidden for preseason**
(and the All-Star game) with the "not available" text. This needs ESPN's season type: parse
`season.type` from the scoreboard event and the summary header (ESPN: 1 = preseason,
2 = regular season, 3 = postseason, 5 = play-in; treat unknown as regular season).

### Pregame point of games already played (my call)

The export carries one snapshot of priors (as of the latest game). For yesterday's finished
games that snapshot already includes the game itself, so their pregame percentage is slightly
optimistic in hindsight. Accepted as **display-only** (training stays leak-free, and it is one
game of a team's season): the footnote says "pregame strength as of <date>". No per-date prior
history is exported.

## Export (`scripts/export_web_data.py`)

A new file `web/public/data/win-probability.json` (name is the builder's call within that
folder), written by the normal export (so `refresh_season.py` refreshes and commits it with the
rest of `web/public/data`). Contents:

- the three coefficients `a, b, c` and the readable `homeCourtPts`, `pointsPerNetRating`,
  `scale`;
- `k`, the season and the as-of date of the priors;
- `teams`: NBA tricode → current pregame net rating (for the newest season in the data);
- metrics for the footnote: training games, held-out games, held-out log-loss of the new model
  and of the baseline, ECE.

Deterministic apart from the as-of date (no wall-clock timestamp). Python tests pin the file's
shape and that the export writes it.

## Browser side (`web/`)

- **Parsing** (`web/lib/live/espn.ts`, existing tests extended):
  - `Play` gains `id` (ESPN play id).
  - `GameSummary` gains `neutralSite: boolean` (from `header.competitions[0].neutralSite`)
    and `espnWinProbability: { playId: string; home: number }[]` (from `winprobability`;
    `homeWinPercentage` is 0–1).
  - `ScoreboardGame` gains `neutralSite: boolean` (from `competitions[0].neutralSite`),
    needed for the pregame prediction of scheduled games, which fetch no summary.
  - Both gain `seasonType: number` (from `season.type`; see "Which games").
  - Missing fields default to `false` / `[]` / `2`.
- **Model** (new pure module in `web/lib/live/`, TDD with `node --test`, `import type` only):
  - `winProbability(model, { margin, secondsRemaining, priorDiff, neutral })` → home
    probability;
  - a series builder: one point per play with a score (elapsed game seconds, home
    probability, home − away margin) plus the pregame point at t = 0;
  - the ESPN series aligned to plays by `playId`.
  - Clock parsing must handle ESPN's "M:SS" and "S.s" formats and overtime.
  - Tests use exact values computed by hand from given coefficients.
- **UI** (layout A, owner choice): a "Win probability" card **directly under the scorebar,
  above the court**:
  - headline percentage per team (tricode + team swatch), a split bar, and a line chart over
    elapsed game time (quarters marked; OT extends the axis). Our model is a solid line, ESPN
    is a dashed line, with a legend; the two are distinguishable without colour.
  - **Score margin on the same chart (owner request, 2026-11-03):** home − away points on a
    **secondary right axis** sharing the X axis, with **0 aligned to the 50% line** so "home
    leads" and "home favoured" sit on the same side. Drawn as a muted stepped area/line behind
    the probability lines (scores change in steps), symmetric scale ±max(|margin|, 10) points
    rounded up to 5, labelled in points, listed in the legend (mockup `wp-layout-v2`).
  - footnote: pregame %, "season net rating + home court", games fitted on, and the held-out
    log-loss of the model vs the baseline.
  - **Scheduled game:** only the pregame prediction (percentages + split bar).
  - **Finished game:** full curve; the final point is 100/0.
  - **In progress:** the curve up to now and the current percentage, refreshed with the existing
    30 s polling. No extra request: the data comes from the same summary.
  - A team missing from the priors, or no model file → "Win probability not available for this
    matchup."
- The model JSON is imported statically (like `web/lib/data.ts` does), so no runtime request.
- Use the `dataviz` skill when building the chart. Colours only from tokens or team accents
  (the design gate). Away/home convention unchanged elsewhere; on the chart, y = home win
  probability, with the top edge labelled with the home tricode (my call).

## Constraints

- TDD by default (Python: pytest with exact values on small synthetic frames; web: `node --test`
  with hand-computed values). Existing gates and tests stay green; the full suite is the gate
  before pushing to `main`.
- No new dependency (Python or npm). Type hints and docstrings on public Python functions.
  Stat functions return copies, never mutate, never produce inf.
- The new Python module is imported only by `scripts/` and tests, never by `dashboard/`.
- Same verification as `/live`: real ESPN data in a real browser (headless Edge with a normal
  user agent), a simulated in-progress game via request interception, then production after the
  push. Vercel previews are SSO-protected.
